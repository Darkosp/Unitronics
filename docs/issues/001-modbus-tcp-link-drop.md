# 001 — Modbus TCP врската паѓа без најава

**Статус:** во анализа · **Заведено:** 2026-08-24
**Метод:** UniLogic проектот (`.ulpr`) е декодиран и прочитан директно од
неговата внатрешна SQL Server база. Наодите подолу се од **реалната
конфигурација**, не претпоставки. VisiLogic страната (`.vlp`) сè уште чека
(Access базата е заштитена со лозинка).

## Симптоми (пријавени)

1. Modbus TCP врската UniStream (Master) ↔ Vision (Slave) прекинува спонтано,
   без најава.
2. Физички рестарт на контролерите **не** ја враќа.
3. **Само** повторен upload на UniLogic апликацијата ја враќа.

## Систем (потврдено од проектот)

```
   Ethernet 10.30.202.0/24
        gateway .100
   ┌────────┴─────────────────────────┐
   │                                   │
UniStream USC-B10-TA30            Vision V130
UniLogic 1.32.98                  VisiLogic
Modbus MASTER                     Modbus SLAVE (ID 255)
 ├ CPU Ethernet  .20  keepalive 7200/75/10
 └ Panel Ethernet .1  keepalive 0/0/0  ──502──▶ .15
     (Modbus Master оди преку овој порт)
```

---

## Наоди (по приоритет)

### F1 — Двата Ethernet порта се на ИСТАТА подмрежа ⭐

`CommunicationsConfiguration`:

- CPU Ethernet: **10.30.202.20** / 255.255.255.0
- Panel Ethernet: **10.30.202.1** / 255.255.255.0

Двата интерфејса се во `10.30.202.0/24`, со ист gateway `.100`. Два NIC-а на
иста подмрежа е класична грешка: TCP стекот не знае детерминистички низ кој
интерфејс да ја пушти сообраќајот, ARP-от се меша, а враќачкиот пакет може да
дојде на „погрешниот" порт. Однесувањето е нестабилно — токму „паѓа без
најава, повремено".

**Провери:** дали двата порта се навистина физички поврзани? Ако да, едниот
треба на друга подмрежа (или изгасен). Modbus кон Vision оди преку Panel
Ethernet (`.1`).

### F2 — TCP Keepalive е ИСКЛУЧЕН на Panel Ethernet ⭐ клуч за „не се враќа"

Portот преку кој Master-от зборува со Vision-от (Panel Ethernet, `.1`) има:

```
TCPKeepaliveTime = 0 ; Interval = 0 ; Retry = 0   →  keepalive исклучен
```

За споредба, CPU Ethernet има `7200 / 75 / 10` (вклучен).

Последица: ако врската умре „тивко" (кабел, switch, reset на Vision socket —
без FIN/RST), UniStream-от **нема механизам да го открие мртвиот socket**. Тој
останува во ESTABLISHED засекогаш, мисли дека е поврзан, и **никогаш не се
обидува да реконектира**. Ова точно го објаснува зошто линкот „не се враќа
сам".

Ова е и најверојатната причина зошто **само upload помага**: upload-от прави
целосно рекомпилирање + рестарт на комуникацискиот стек и нова чиста TCP
сесија, што power cycle во некои случаи не го постигнува ако спротивната
страна сè уште држи заглавен socket.

**Провери / поправи:** вклучи TCP Keepalive на Panel Ethernet (пр. 30 s / 5 s
/ 3). Или префрли го Modbus Master-от на CPU Ethernet кој веќе има keepalive.

### F3 — Пол-ирање на 100 ms × 30 трансакции кон еден V130 ⭐ веројатен ОКИДАЧ

`MODBUSSlaveAddressType`: слејвот `Modbus_TCP_V_130` има **30 трансакции**
(19 FC03 read, 3 FC01 read coils, 6 FC15 write coils, 2 FC16 write regs),
**сите поставени на `EveryPeriod = 100 Milliseconds`**.

Тоа е ~300 Modbus TCP барања во секунда кон еден мал, стар Vision V130, со
`ResponseTimeout = 1000 ms`. V130 има ограничен процесор и **ограничен број
сокети**. Ваков интензитет со тек на време го затнува неговиот Modbus/TCP стек
— socket-от се заглавува, а бидејќи F2 го спречува Master-от да го забележи,
целата врска замрзнува.

**F3 е окидачот (зошто паѓа), F2 е причината (зошто не се враќа).** Двете
заедно го објаснуваат целиот сет симптоми.

**Провери / поправи:** намали го пол-ирањето драстично. Реткост од 100 ms е
непотребна за повеќето процесни величини — 500 ms до 1 s е сосема доволно и
го растоварува V130. Групирај соседни адреси во еден повеќерегистарски read
наместо многу поединечни.

### F4 — Мртов „Remote Slave1" на 0.0.0.0

`MODBUSRemoteSlaveConfiguration` содржи слејв со IP `0.0.0.0`, 4 трансакции,
под сериски master. Веројатно остаток. Не е причина за падот, но да се
исчисти за да не создава грешки во логовите.

## Што овие наоди ГО ИСКЛУЧУВААТ

- **Заглавен socket само на Vision (socket exhaustion) како единствена
  причина** — F2/F3 на UniStream страната подобро го објаснуваат зошто upload
  само на UniLogic помага.
- **Хардверски дефект** — не се поправа со upload.

## Препорачан редослед на дејства

1. **F1 прво** — потврди ја физичката топологија. Ако двата порта се на иста
   мрежа физички, тоа само по себе може да е причината. Ова е бесплатно за
   проверка.
2. **F2** — вклучи keepalive на Panel Ethernet (или премести Modbus на CPU
   Ethernet). Мала измена, голем ефект.
3. **F3** — олади го пол-ирањето на 500 ms–1 s и групирај читања.
4. **F4** — исчисти го мртвиот слејв.

Сите четири се измени **само во UniLogic**. Регистарските адреси не се менуваат
→ VisiLogic страната останува иста. Тоа значи дека можат да се тестираат без да
се дира Vision-от.

## Дополнителни подобрувања (по стабилизација)

- **Heartbeat регистар** — Master пишува бројач што расте; Vision проверува
  дали расте. Двете страни знаат дека линкот е ЖИВ, не само дека TCP постои.
- **Watchdog реконекција во ladder** — ако нема успешна размена > N s →
  присилен Disconnect/Connect (без retained флагови во условот).
- **Дијагностички HMI екран** — број неуспешни трансакции, последен error код,
  време од последна успешна размена, број реконекции. Следниот пат — фотографија
  наместо погодување.
